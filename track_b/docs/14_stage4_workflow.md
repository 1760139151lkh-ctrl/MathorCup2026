- 本窗口为主参谋/集成者。用户已授权创建四个聊天分支，向它们发送任务、读取进展、组织交接；不要求用户手动转发。

- 队员保留核心建模、算法、求解、科学分析及最终采用判断；研究窗可开展资料核查、候选方案比较、质量诊断和最小技术可行性实验。
- 恢复顺序：`../STATUS.md` → 本文 → `13_stage3_handoff.md` → `../research/qN/TASK.md` → 该问`HANDOFF.md`。
- 具体聊天ID、worktree路径、分支、起点提交与运行证据由主参谋维护在`../audit/stage4/workspaces.json`。不得仅凭继承的聊天记忆判断当前状态。

## 基线与隔离

1. 保存阶段1—3准备成果的本地提交，再保存任务书、协议和输入清单的共同起点提交。
2. `../audit/stage4/baseline_manifest.json`绑定准备提交，并逐文件冻结原始B赛道/规则/模板、共享派生数据、已有审计与阶段3处理脚本/配置/依赖锁。清单不包含自身和后续各问产物。
3. 四窗从同一共同起点开始，各问只能写`track_b/research/qN/`。原始资料、`track_b/data/`、旧审计、公共脚本/配置/依赖、全局状态均为只读输入。
4. 每个worktree用自己的`track_b/.venv`，按`requirements-lock.txt`重建，不复制带绝对路径的旧venv，不改系统或Anaconda环境。
5. 启动时核对Git起点、输入哈希、工作目录、版本锁和六种真实格式；交接前再次核对冻结输入与文件责任。运行`stage4_workspace.py verify`，不要重跑会更新公共审计的阶段3脚本。

## 每轮交付与联合审查

流程：共同基线 → 四窗并行首轮 → 主参谋联合审查 → 队员确认路线 → 分问正式基线 → 跨问验证 → 论文证据整理。

每窗首轮交付`HANDOFF.md`、可复跑小实验脚本、机器结果/必要图表、方案比较、缺口和跨问需求。交接数据最小字段见`../config/stage4_contract.json`：输入版本/哈希、事件及物理阶段、UTC时钟与误差、空间对象/CRS、单位/QC/累计边界、数据可用时刻、探索/校准/验证角色。null表示尚未核实，不自动补齐。

主参谋在各窗到达检查点时读取结果，按依赖向相关窗发送经审核的交接；不需要等四问同一时刻结束。新增公共口径记录版本、理由、受影响窗口与需要重做的实验。只在本轮有新变更或问题时重跑相关验证。

首轮联合审查检查：输入一致；证据与推断区分；上下游时钟/单位/参数一致；是否存在事后信息或循环验证；方法是否有数据支持；未决事项是否有负责人和下一动作。

## 形成正式结论的门槛

- Q1：固定质量规则、事前窗口和对照，说明排序稳定性和单事件解释范围。
- Q2：临界条件有机制/样本约束；不足时仅给有明确适用条件的情景范围。
- Q3：标签、历史信息截止、独立验证单位可核验。基线中合格独立历史事件为0，滚动窗口不能冒充独立事件数，名义95%不能冒充已验证95%覆盖。
- Q4：源区到目标地形连续、初值参数可追溯；区分数值检查、物理合理性、事件校准及独立验证。证据不足时保持情景实验标识。

部署与论文最终提交不在本轮范围。四窗完成首轮后停在联合审查点，等待主参谋反馈；不自行宣称正式科学路线已被队员接受。
